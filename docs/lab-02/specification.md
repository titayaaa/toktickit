# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Deliver the Requester-facing UI and supporting API for creating IT support tickets, uploading attachments, viewing the My Tickets list, and viewing ticket details. This sprint uses a temporary Development Requester selection mechanism instead of real authentication to simulate the logged-in user context.

## 2. Stakeholder Request Interpretation
The IT department needs a professional end-user ticketing interface. Requesters should be able to submit a ticket with a category, related system, priority, and up to 5 attachments (max 5MB each). They can view all their tickets in a searchable, filterable, sortable, and paginated "My Tickets" list. They can also view ticket details and manage attachments via soft-removal. To facilitate testing before login is implemented in Lab 3, a "Development Requester Selection" screen is needed to act as the current user.

## 3. Scope
### Included
- Development Requester selection and context switching (testing mechanism).
- Ticket creation with system-generated official Ticket Number.
- My Tickets list with search, filtering, sorting, and pagination.
- Requester Ticket Detail screen (read-only view).
- Attachment lifecycle: upload, download, soft removal, and metadata display.
- PostgreSQL models and seed data for Tickets, Attachments, Categories, Related Systems, and Requesters.

### Excluded
- Real authentication, login, logout, passwords, sessions, or tokens.
- IT Staff workflow (queues, reassignment, changing IT Priority).
- Ticket collaboration (Public Comments, Internal Notes, Actions Taken).
- Ticket lifecycle beyond "New" status (resolution, closing).
- Administration functions.

## 4. Functional Requirements
- **FR-01**: The system must provide a Development Requester Selection screen to set the active user context.
- **FR-02**: The system must allow the selected Requester to create a Ticket specifying Category, Related System, Summary, Description, and Requested Priority.
- **FR-03**: The system must allow the Requester to upload up to 5 permitted attachments per ticket.
- **FR-04**: The system must display a paginated My Tickets list for the selected Requester, supporting search, filtering, and sorting.
- **FR-05**: The system must allow the selected Requester to view their own Ticket Detail in read-only mode.
- **FR-06**: The system must allow the Requester to soft-remove their own attachments, rendering them invisible for download.
- **FR-07**: The system must prevent Requesters from viewing or accessing tickets or attachments owned by other Requesters.

## 5. Business Rules
- **BR-01**: The official Ticket Number is generated by the backend and must be unique.
- **BR-02**: A new Ticket begins with Current Status `New`.
- **BR-03**: Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- **BR-04**: Attachments are limited to JPG/JPEG, PNG, WEBP, and PDF types, with a maximum size of 5 MB per file, and a maximum of 5 active attachments per ticket.
- **BR-05**: Attachment removal must be implemented as soft removal. Removed files must not be downloadable or previewed, and a removal reason must be recorded.
- **BR-06**: Required fields for Create Ticket include Summary (1-200 chars), Description (1-2000 chars), Category, Related System, and Requested Priority.
- **BR-07**: Inactive Requesters must not appear in the Development Requester selector.
- **BR-08**: A Ticket must be strictly owned by the currently selected Requester.
- **BR-09**: The system must implement duplicate-submission prevention on the Create Ticket form (e.g., disabling the submit button while processing).
- **BR-10**: If ticket submission fails, the data entered in the form must be retained so the user does not have to re-enter it.
- **BR-11**: The UI must distinguish between an "empty state" (the user has never created any tickets) and a "no-results state" (the user's search/filter criteria yielded no tickets).

## 6. UI Specification Summary
The UI follows the "Zen Green Theme" detailed in `ui-spec.md`.
- Primary actions use Primary green (`#006B3C`), secondary accents use Secondary green (`#0B7A46`).
- The Create Ticket screen separates system-generated fields (top) from classification, text input, and attachments.
- Required fields are marked with a red asterisk.
- My Tickets includes a responsive table/card list, search bar, filters, and pagination controls.
- Validation messages appear below their respective fields, not grouped at the top.
- Detailed visual constraints and component states are defined in `ui-spec.md`.

## 7. Data Changes
### Models
- **Ticket**: `id` (PK), `ticketNumber` (unique), `requesterId` (FK), `categoryId` (FK), `relatedSystemId` (FK), `summary`, `description`, `requestedPriority`, `itPriority`, `currentStatus`, `createdAt`, `updatedAt`.
- **Attachment**: `id` (PK), `ticketId` (FK), `originalFilename`, `storagePath`, `mimeType`, `sizeBytes`, `removedAt`, `removalReason`, `createdAt`.
- **Category**: `id` (PK), `name` (unique), `isActive`.
- **RelatedSystem**: `id` (PK), `name` (unique), `isActive`.
- **RequesterUser**: `id` (PK), `name`, `email` (unique), `isActive`.

### Enums
- `TicketPriority`: `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`
- `TicketStatus`: `NEW`, `OPEN`, `IN_PROGRESS`, `PENDING`, `RESOLVED`, `CLOSED`, `CANCELLED`

### Seed Data
- Categories: Account and Access, Hardware, Software, Network.
- Related Systems: Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer, Corporate Laptop.
- Requesters: At least 4 active, 1 inactive.

## 8. API Contract
Refer to `api-spec.md` for full details.
- `GET /api/requesters`: Returns active Requesters.
- `POST /api/tickets`: Creates a ticket (returns 201).
- `GET /api/tickets`: Retrieves paginated ticket list for the active Requester.
- `GET /api/tickets/:id`: Retrieves ticket details (must enforce ownership).
- `POST /api/tickets/:id/attachments`: Uploads an attachment.
- `DELETE /api/tickets/:id/attachments/:attachmentId`: Soft-removes an attachment.

## 9. Acceptance Criteria
- **AC-01**: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- **AC-02**: Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- **AC-03**: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned (403 Forbidden).
- **AC-04**: Given an attachment larger than 5MB, when the user uploads it, then it is rejected with an error message and not saved.
- **AC-05**: Given valid search and filter parameters, when the Requester views My Tickets, then only matching tickets owned by them are displayed, paginated according to the request.
- **AC-06**: Given an active attachment, when the Requester removes it and provides a reason, then the attachment is marked as soft-removed and can no longer be downloaded.

## 10. Definition of Done
- Implementation of all approved scope and business rules.
- Satisfaction of all Acceptance Criteria.
- Passing unit, API, UI, and E2E tests, fully traceable in `tests.md`.
- Conformance to data, API, UI, validation, and responsive specifications.
- Correct handling of success, failure, loading, empty, and boundary cases.
- All code is merged via PR through `lab2-staging` to `main`.
- Clean visual inspection across Desktop, Tablet, and Mobile viewports.

## 11. Assumptions and Decisions
- **Decision**: Soft removal of attachments will keep the database record and physical file (or just the record, depending on storage strategy), but flag it with `removedAt`.
- **Decision**: The `requesterId` will be passed in the `Authorization` header as a mock token (e.g., `Bearer dev_requester_1`) for API requests to simulate future authentication seamlessly without modifying endpoints later.
- **Assumption**: A Ticket's official Number format is `TKT-YYYY-XXXXXX` (e.g. TKT-2026-001234).
